# 00-238 发布后观察与旧运行时退场 - 技术设计

_Requirements: 3.1-3.6, 4, 5_

## 1. 观察阶段

```text
CUTOVER_OK -> OBSERVING -> STABLE
                  |
                  +-> EXTENDED_OBSERVATION
                  +-> ROLLED_BACK
```

- `OBSERVING`：新候选承接流量，旧容器保留。
- `STABLE`：达到观察窗口和指标门槛。
- `EXTENDED_OBSERVATION`：非致命异常需继续观察，不能退场。
- `ROLLED_BACK`：已回切旧 upstream 或暂停小程序新版本。

## 2. 指标与门槛

正式阈值应结合当前基线确认，最低门禁：

- 核心 API 无持续 5xx；单次瞬态需有解释和恢复。
- 登录、资料保存、素材绑定、公开分享没有新增 P1/P0。
- 数据库连接池无耗尽、死锁或缺列/缺表异常。
- Redis/Nacos/COS 连接稳定。
- 测试 schema/Redis/COS 没有生产目标写入。
- 历史账号回归不出现数据不可见或旧字段覆盖。

每 5-10 分钟聚合一次，保留时间序列和事件标记。

## 3. 发布后回归

切流后最小回归：

1. 正式 API docs/health。
2. 管理端首页和登录。
3. 历史账号：资料、经历、intro、素材、旧分享、实名只读。
4. 新账号：一次资料保存、一次媒体绑定、一次演员卡草稿回读。
5. 匿名访问一张旧分享卡和一张新发布卡。
6. 测试域名仍访问测试服务和测试 schema。

回归产生的测试数据使用明确内部账号并记录，可在后续清理 Spec 中处理；不能删除真实用户数据。

## 4. 回切 Run Card

回切卡至少记录：

- 触发时间、指标和 correlation id。
- 当前候选、旧容器、旧 upstream。
- Nginx 配置备份和回切命令/审批人。
- 回切前后 API smoke。
- 切流后新增写入保护措施。

回切动作：

1. 停止新版本继续承接流量（按 Nginx upstream/服务编排）。
2. 回切旧 upstream。
3. `nginx -t` + reload。
4. 验证正式 API/管理端/旧小程序。
5. 保留新 Schema 和数据，单独分析应用兼容问题。

## 5. 小程序版本回退

- 后端保持向后兼容，不因小程序审核失败回退数据库。
- 若新小程序有严重运行问题，使用微信版本管理暂停/回退。
- 继续监控旧版本调用的新后端合同。

## 6. 旧容器退场前清单

- 观察窗口完成。
- 无未关闭 P0/P1，P2 有明确接受。
- 正式历史账号回归通过。
- API/管理端/小程序正式 smoke 通过。
- 旧 JAR、镜像、compose、Nginx、DB backup 和切流记录保存。
- 测试双环境 preflight 通过。
- 用户/发布负责人明确同意停止旧容器。

## 7. 长期双环境治理

- 测试每次候选前从生产副本重建或按数据策略刷新。
- 测试 schema 不自动回写生产。
- 测试外部资源和账号按批次清理。
- 每次正式发布都重新引用 `00-231` 至 `00-238` 相关证据，不复制旧结论。

## 8. 回滚边界

旧容器停止后仍保留可重启资源。删除旧镜像、JAR、备份和 Nginx 回切配置需要新授权；删除新表/列/关系不属于本 Spec。
