# 技术设计草案

_Requirements: 3.1-3.4_

> 仅设计；用户尚未确认历史卡生效策略与完整实现方案。

## 1. 方案选择

- 方案A：只在现有页面加若干圆角/颜色参数。成本低，但不足以满足模块位置、顺序和页面装修，排除作为完整目标。
- 方案B（建议）：受控模块Schema + 后台可视化装修器 + 小程序通用渲染器。后端控制页面定义，客户端负责原生组件落地与交互，兼顾可配置、长页适配和现有分包边界。
- 方案C：后端下发任意HTML/脚本或把整个页面画成图片。前者不适配当前原生小程序渲染体系；后者丢失视频/PDF/联系交互且样式编辑要重绘，不作为本次方案。

## 2. 端到端结构

```text
后台风格模板/背景管理
  -> 可视化装修（模块列表 + 画布 + 属性面板）
  -> 后端Schema校验 / 草稿 / 发布版本 / 回滚
  -> 卡片有效模板解析 + 演员真实数据 + 公开显隐约束
  -> generate / view 共用渲染器

人物照片 -> AI首图任务 -> 默认装修模板
人物照片 + 后台背景 -> 双图合成任务 -> 背景关联装修模板
```

“后端控制”指后端发布页面Schema及允许的数据绑定，不是服务端生成DOM、任意执行布局代码，或让AI生成带文字的整页位图。

## 3. 配置模型（逻辑草案，非已定数据库结构）

- 页面标识：schemaVersion、templateId、templateVersion、最小renderer能力版本。
- 全局主题：语义颜色、字体层级、统一圆角/间距/内容宽度。
- Hero：图片显示方式、裁切焦点、覆盖区域、遮罩与容器内位置。
- modules：受支持type、稳定id、enabled、order、受控数据绑定、layout与style覆盖。
- assets：后台受管背景资源引用；与人物来源和AI结果独立。
- actions：受控的分享、联系、预览PDF等动作；卡主发布/生成动作仍由外壳管理，不给公开观看者配置出发布权限。

所有数值定义单位、范围与默认值；采用750设计宽度坐标归一化和内容流布局。排版属性可配置不等于接受无限CSS。具体Schema与API需后续契约设计和测试，不在此草案伪装已实现。

## 4. 发布与数据边界

- 编辑草稿和已发布版本分开，发布原子切换，并保留可回滚版本。
- 历史卡是否跟随新版本为待确认产品策略；后端统一解析，预览/分享不能各自取latest造成分叉。
- 绑定路径白名单；样式配置不能绕过showContact/showVideo/showAttachment或获取卡主私有素材。
- PDF/视频/照片引用既有公开可用资源与签名规则，不将签名URL写入模板长期保存。
- 后台手机预览使用脱敏示例或授权预览数据，不假造真实粉丝/热度。

## 5. AI任务隔离

- 任务身份至少包含生成模式、人物稳定来源、背景稳定来源/版本及生成配置版本。
- 纯布局样式版本与图像生成指纹分离，改圆角不触发AI；真正的合成素材/指令变更才使生成结果失效。
- 双图Provider适配必须先确认当前运行Provider输入能力；不支持时明确失败或不可用，不静默按单图生成。
- 结果回写检查当前模式及图像输入指纹，防切换背景后旧任务覆盖新首图；隐私素材异步执行时即时签名。

## 6. 实施边界与验收计划

1. 先确认历史卡发布策略、模块展示合同和两种模式交互；再细化API/存储/Provider能力。
2. 对Schema校验、默认继承、版本解析、公开隐私、图像/布局指纹分别先写失败测试。
3. 后台编辑回读、渲染器按同一配置展示、默认模式/指定背景模式、长文本/空数据/多照片/视频/PDF、安全区均验收。
4. 新旧客户端兼容、旧视觉门禁替换、包体审计和固定dev运行核验后才准备新的测试Candidate；当前体验版不受本设计修改影响。
