# 00-69 当前阶段分享与数据分析架构重构（Current Phase Share Analytics Architecture Refactor）

> 状态：规划中 | 优先级：最高 | 依赖：00-27 mini-program-frontend-architecture，00-28 architecture-driven-delivery-governance，00-62 current-phase-minimal-share-card-mvp-alignment，00-68 current-phase-share-runtime-and-poster-capability-alignment
> 记录目的：把用户最新确认的“前端仅保留登录/注册、首页、记录、个人中心；后台收口为控制台/渠道分析与用户中心；后端负责链接整体流程与统计”的当前架构，提升为一条独立重构 Spec，并明确旧代码删除边界，防止继续在当前工程里保留旧演员招募、旧会员中心、旧邀请/命理独立入口和旧后台多业务域并存。

## 1. 背景

当前仓库已经多轮沿旧主线演进，代码中同时存在：

- 前端新的分享名片 MVP 链路
- 旧演员 / 剧组招募链路页面
- 旧会员 / 命理 / 邀请独立功能页
- 旧后台多业务域菜单（verify / referral / recruit / membership / payment / refund / system 等）

但用户最新已明确新的当前架构：

### 1.1 前端

1. 登录 / 注册
2. 首页
3. 记录
4. 个人中心（我的）

其中：

- 首页只围绕 3 种示例风格（都市 / 古风 / 经典）分享和 1 个操作视频展开
- 用户最多创建 3 种分享海报
- 记录页只看“我打开过别人分享的卡片或海报”
- 个人中心只保留“个人档案、创建分享、退出登录”

### 1.2 后台管理

1. 控制台 / 渠道控制
2. 用户中心

其中：

- 控制台负责分析“用户通过什么渠道进入（卡片 / 海报）”
- 用户中心负责查看用户个人信息与已创建的分享卡片

### 1.3 后端

- 后端只负责串联整体流程与数据统计闭环

如果不先建独立 Spec，后续极易继续出现：

- 新架构页面改了一半，旧页面和旧菜单还继续保留
- 前端 visible 入口虽变了，但旧接口和旧代码仍持续扩散
- 后台保留大量与当前架构无关的菜单和页面
- 删除旧代码时没有边界，最终再次回退成“新旧混搭”

## 2. 范围

### 2.1 本轮必须处理

- 固化当前阶段新的前端 / 后台 / 后端信息架构
- 明确当前阶段主链页面、菜单、接口与目录边界
- 明确哪些旧代码必须删除，哪些只能下沉为兼容层或治理脚本
- 为后续真实代码重构提供单一上位入口

### 2.2 本轮不处理

- 一次性完成所有代码实现
- 二期商业化、支付、退款、复杂会员体系扩展
- 微信官方能力扩展
- 完整视觉稿重做

## 3. 需求

### 3.1 前端信息架构

- **R1** 小程序当前阶段只允许围绕以下信息架构组织：
  - 登录 / 注册
  - 首页
  - 记录
  - 个人中心（我的）
- **R2** 首页必须只围绕“分享风格卡片 + 操作视频”组织，不再承载旧演员公开列表、角色列表、剧组列表或招募广场。
- **R3** 首页示例风格必须明确收口为 `都市 / 古风 / 经典` 三类，旧 `general / urban / commercial / costume / artistic` 的技术口径不得直接裸露为当前产品主文案。
- **R4** 记录页必须只承载“我打开过别人分享的卡片或海报”，不得混入旧广场浏览、旧搜索浏览或无关历史记录。
- **R5** 个人中心当前阶段只保留：
  - 个人档案
  - 创建分享
  - 退出登录
- **R6** 当前前端 active 主链不得继续保留旧“投递反馈记录”“剧组资料”“角色详情 / 投递确认 / 我的投递 / 招募管理”等旧业务入口。

### 3.2 前端旧代码删除边界

- **R7** 以下页面 / 模块必须纳入删除或彻底退出 active 主链范围：
  - `pages/role-detail`
  - `pages/apply-confirm`
  - `pages/my-applies`
  - `pages/apply-detail`
  - `pages/project/create`
  - `pages/project/role-create`
  - `pages/apply-manage`
  - `pages/company-profile/edit`
  - `pages/role-select`
  - 历史残留 `credit-*` 页面
- **R8** 以下旧分包页面必须评估并收口，不得继续作为当前主架构独立入口存在：
  - `pkg-card/membership`
  - `pkg-card/invite`
  - `pkg-card/fortune`
  - `pkg-card/verify`
- **R9** 若某个旧页面当前仍有数据依赖或兼容责任，必须在 Spec 中明确其是“兼容保留层”，而不是继续伪装成当前产品主入口。
- **R10** 前端 active 路由、`pages.json`、tabBar 和页面入口 helper 必须与新架构一致，不能页面删了但路由和跳转仍保留旧入口。

### 3.3 后台管理架构

- **R11** 后台当前阶段只允许收口为两类主菜单：
  - 控制台 / 渠道分析
  - 用户中心
- **R12** 控制台必须围绕分享渠道分析组织，重点至少包含：
  - 用户分享次数
  - 通过分享进入次数
  - 卡片 / 海报来源统计
  - 二次回访率
  - 留存 / 活跃指标
- **R13** 用户中心必须围绕用户与分享卡片治理组织，至少包含：
  - 用户个人信息
  - 用户已创建分享卡片
  - 相关分享状态或摘要
- **R14** 当前后台 active 菜单中不再允许继续保留旧多业务域并列结构，如：
  - verify
  - referral
  - recruit
  - membership
  - payment
  - refund
  - system（非当前必要治理项）
- **R15** 若旧后台页面暂时仍需保留为运维 / 治理 / 数据迁移工具，必须从当前用户可见主菜单中移出，并定义为迁移期治理入口，而不是继续作为正式业务架构的一部分。

### 3.4 后端能力边界

- **R16** 后端当前阶段必须围绕以下能力收口：
  - 登录 / 注册
  - 用户档案
  - 分享卡片创建 / 编辑 / 查询
  - 查看历史
  - 分享埋点 / 渠道统计
  - 用户与分享卡片管理
- **R17** 后端不得继续以旧演员招募、旧邀请裂变、旧会员中心、旧命理独立主线作为当前产品架构中心。
- **R18** 后端必须为“分享次数、分享进入次数、回访次数、留存 / 活跃度”提供统一数据事实源，不得把分析口径散落在前端页面内联统计。
- **R19** 与当前架构无关的旧控制器、DTO、服务实现必须纳入删除、收口或迁移名单，不得继续无限增长。

### 3.5 统计与存活率数据

- **R20** 当前架构必须把“数据埋点与统计”提升为正式能力，不再只是页面附属信息。
- **R21** 至少要把以下统计口径纳入统一架构：
  - 用户分享了几次
  - 别人通过分享进入了几次
  - 用户是否再次进入分享页面
  - 哪种分享方式带来更多进入（卡片 / 海报）
  - 哪种风格更容易被点击（都市 / 古风 / 经典）
  - 用户是否由“打开别人分享”转化为“创建自己的分享”
  - 次日留存 / 7 日留存 / 活跃用户数
- **R22** 上述统计口径必须服务于“小程序存活率提升”目标，而不是只做后台展示字段堆砌。

### 3.6 治理要求

- **R23** 本轮必须通过独立 Spec 固化当前架构重构和旧代码删除计划，不能只在聊天中口头描述。
- **R24** 本轮 Spec 必须明确列出：
  - 新架构保留项
  - 旧代码删除项
  - 兼容保留项
  - 后续分阶段执行顺序
- **R25** 在未核实完依赖前，不允许直接大面积删除代码；必须先通过本 Spec 明确删除边界和验收方式。
