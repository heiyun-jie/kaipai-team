# 00-62 当前阶段最小分享名片 MVP 架构对齐（Current Phase Minimal Share Card MVP Alignment）

> 状态：规划中 | 优先级：最高 | 依赖：00-27 mini-program-frontend-architecture，00-28 architecture-driven-delivery-governance，00-52 current-phase-invite-record-page-boundary-alignment，05-11 fortune-driven-share-personalization
> 记录目的：把当前阶段产品主线从“演员公开列表 + 旧分享页拼接”正式改写为用户明确给出的最小 MVP 边界，统一首页、历史、个人中心、档案/名片拆分、默认普通卡、邀请解锁风格和联系方式申请/同意流程，防止前后端和后台继续按旧口径各自推进。

## 1. 背景

当前代码和文档仍残留多条旧主线：

- 首页仍长期背着演员列表 / 角色列表 / 历史公开浏览口径
- `actor profile` 与 `share card` 的数据职责仍有混用
- 分享页、邀请页、公开页和个人中心对“名片到底是什么”没有完全统一
- 联系方式仍缺少“申请 -> 持卡人同意 -> 查看电话”的闭环定义
- 用户已明确给出新的最小 MVP 边界，如果不先升成独立 Spec，后续前端改一半、后端补一半、后台再跟一半，会再次分叉

## 2. 范围

### 2.1 本轮必须处理

- 小程序 Tab 信息架构重排
- 首页从公开列表切换为“可分享卡片 / 风格模板”主入口
- `用户档案` 与 `分享卡片` 的模型拆分
- 默认普通卡自动补齐
- 风格解锁与邀请人数阈值改为后台可配
- “查看历史”与“已联系列表”边界定义
- 联系方式申请 / 同意 / 查看闭环定义
- 个人中心模块收口
- `00-28` 主路线、总体评估、结构图、索引与映射回填

### 2.2 本轮不处理

- 二期“平台创建通告”产品
- 广场式演员公开列表恢复
- 真实支付、会员商业化与复杂营销
- 微信官方能力是否接入
- 全量 UI 细节定稿与所有页面代码实现

## 3. 需求

### 3.1 信息架构与可见范围

- **R1** 小程序当前阶段底部 Tab 必须收口为三项：
  - `可以分享的卡片`
  - `查看历史`
  - `个人中心`
- **R2** 首页不得再以演员公开列表、角色列表或通告列表作为当前阶段主入口。
- **R3** 首页必须以“可分享卡片 / 风格模板”作为唯一主入口，用户进入后优先看到自己可创建、可编辑、可分享的卡片风格。
- **R4** 其他用户当前阶段只能看到：
  - 自己收到或打开过的分享卡片
  - 分享给自己的公开名片页
  不得继续提供广场式公开浏览入口。
- **R5** 若用户在某一列表场景下暂时没有任何可展示数据，页面必须显示明确空态引导，例如“先创建一张分享卡片吧”，不得回退展示旧演员列表。

### 3.2 用户档案与分享卡片拆分

- **R6** `用户档案` 必须定义为通用基础资料，供所有风格卡片复用，不得再把风格展示字段直接混进档案主模型。
- **R7** `分享卡片` 必须定义为独立实体，至少包含：
  - 所属用户
  - 风格模板
  - 卡片展示配置
  - 分享状态
  - 联系方式授权状态摘要
- **R8** `pages/actor-profile/edit` 当前阶段只负责编辑通用档案，不再承担某张风格卡片的主编辑职责。
- **R9** “我的名片”必须改为卡片列表，而不是单张卡片入口；列表项可点击进入对应卡片编辑页。
- **R10** “新增分享卡片”必须成为卡片列表主操作，不再沿用“分享小程序”作为底部主按钮。

### 3.3 默认卡、风格模板与邀请解锁

- **R11** 当前阶段基础风格模板至少要显式包含 `普通`、`都市`、`古代` 三类。
- **R12** 新用户注册或首次补链路时，系统必须自动拥有一张默认 `普通` 分享卡片。
- **R13** 若因历史数据或补偿失败导致用户没有任何卡片，系统必须优先补默认 `普通` 卡；补齐前页面只能展示空态与引导，不得静默报错。
- **R14** 其他风格的解锁条件必须由邀请人数驱动，不得散落在前端页面内联判断。
- **R15** 风格解锁阈值必须由后端 / 后台统一配置，前端只能消费统一结果。
- **R16** 风格是否已解锁、还差多少邀请人数、解锁后可创建哪些卡片，必须由单一事实源输出，避免前端、后端、后台各算一套。

### 3.4 历史与公开查看边界

- **R17** `查看历史` 必须记录用户真正看过的分享卡片或公开名片，不再混入广场浏览或搜索结果。
- **R18** 历史记录至少应包含卡片标识、风格、查看时间、持卡人摘要与当前联系方式授权状态。
- **R19** 公开详情页必须以“某一张被分享出来的卡片”为核心，而不是重新退回通用演员详情浏览页。

### 3.5 联系方式申请 / 同意闭环

- **R20** 查看联系方式必须改为授权链路：
  - 查看方点击 `申请`
  - 持卡人确认 `同意` 或 `拒绝`
  - 只有同意后，查看方才可见联系电话
- **R21** 当前阶段公开名片页底部主操作必须围绕“申请联系方式 / 查看授权结果”展开，不得默认直接展示电话。
- **R22** 联系方式授权状态必须和具体卡片、具体申请关系关联，不能只按用户全局布尔值粗暴处理。
- **R23** 持卡人必须存在最小处理入口，用于查看并处理待审批的联系方式申请。
- **R24** 个人中心必须新增“已联系的列表”，用于查看已经获批并可联系的对象清单。

### 3.6 个人中心收口

- **R25** `个人中心` 当前阶段必须保留：
  - 档案信息
  - 实名认证
  - 已联系的列表
  - 我的名片
- **R26** `投递反馈记录` 必须从当前 MVP 个人中心隐藏。
- **R27** `名片能力中心` 不得继续按旧架构直接保留为当前阶段主入口；若继续存在，必须先重新评估并纳入新的信息架构说明。
- **R28** 与旧分享主线重复、噪音化或只服务旧邀请页叙事的模块，必须从个人中心移除或降级。

### 3.7 后端与后台能力边界

- **R29** 后端必须提供独立的卡片列表、卡片模板、风格解锁、历史记录、联系方式申请 / 审批能力，不得继续只靠旧 `actor profile + personalization` 拼接假装闭环。
- **R30** 后台必须至少具备：
  - 风格模板启停与可用性管理
  - 邀请解锁阈值配置
  - 默认普通卡补偿 / 初始化策略
  - 联系方式申请与审批记录治理入口
- **R31** 与风格解锁、资格判断、联系方式授权相关的展示文案和状态，必须服从单一来源规则，不得再分散到页面各自硬编码。
