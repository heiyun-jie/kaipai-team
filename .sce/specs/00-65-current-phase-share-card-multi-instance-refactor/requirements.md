# 00-65 当前阶段分享卡多实例模型重构（Current Phase Share Card Multi-Instance Refactor）

> 状态：规划中 | 优先级：最高 | 依赖：00-62 current-phase-minimal-share-card-mvp-alignment，00-63 current-phase-share-card-latest-state-alignment，00-10 platform-admin-backend-architecture
> 记录目的：把当前“同一用户同一风格只保留一张卡”的模型问题正式升级为独立 Spec，明确模板资格与卡片实例必须解耦，确保“新增分享卡片”是真正新增一个新的存储实例，而不是复用同风格旧卡。

## 1. 背景

当前用户明确指出：

- 点击“新增分享卡片”和“编辑分享配置”，实际修改的是同一套卡
- 这不符合“新增一套就新增一套存储”的预期

后端当前实现中：

- `UserShareCardServiceImpl.createCard(...)`
- 通过 `findOwnedCard(userId, sceneKey)` 与 `ensureOwnedCard(...)`
- 保证了“同用户 + 同风格 = 一张卡”

这意味着当前系统把“模板资格”和“卡片实例”混成了一件事：

- 解锁了某个风格
- 就默认只能拥有该风格的一张卡

这已经与用户当前产品意图冲突，因此必须拆成独立 Spec 处理。

## 2. 范围

### 2.1 本轮必须处理

- 明确模板资格与卡片实例解耦
- 明确新增分享卡片必须真正新建 `UserShareCard` 实例
- 明确前端 / 后端 / 后台在多实例模型下的边界变化
- 明确默认普通卡与风格解锁在多实例模型下的保留规则

### 2.2 本轮不处理

- `pkg-card/actor-card/index` 页面旧会员 / 命理 / 受众视角 UI 清理
- 代表照片 / 高亮经历 / 配色编辑器细节
- 公开页 UI 视觉重做
- 模板风格库扩容

## 3. 需求

### 3.1 模板资格与卡片实例解耦

- **R1** `ShareCardTemplate` 必须只表示“可用风格模板 / 可创建资格”，不得再被等同于真实卡片实例。
- **R2** `UserShareCard` 必须表示真实的用户持有卡片实例；同一用户可以在同一模板下拥有多张卡片。
- **R3** 风格解锁表示“可以创建这种风格的卡”，而不是“系统自动唯一生成一张这种风格的卡”。

### 3.2 新增卡片语义

- **R4** 当用户点击“新增分享卡片”时，系统必须新建一条新的 `UserShareCard` 记录，而不是复用同风格已有卡片。
- **R5** 新建卡片后，必须生成该实例自己的：
  - `shareCardId`
  - 展示配置绑定
  - 分享路径
  - 历史 / 联系方式授权归属
- **R6** “编辑分享配置”只允许编辑当前已选中的具体卡片实例，不得隐式指向同风格下的另一张卡。

### 3.3 默认普通卡规则

- **R7** 默认普通卡仍然必须保留为系统初始化与补偿链路的基础卡。
- **R8** 默认普通卡存在，不得阻止用户继续新增其它普通风格卡；但系统必须明确哪一张是默认卡。
- **R9** 默认卡与非默认卡的行为差异必须显式化，例如：
  - 是否允许删除
  - 是否作为默认公开分享入口
  - 是否在后台治理中单独标识

### 3.4 前端边界

- **R10** 卡片列表页必须展示真实卡片实例列表，而不是“按风格去重后的卡片列表”。
- **R11** 列表页必须支持区分：
  - 模板名称
  - 实例名称或实例摘要
  - 是否默认卡
  - 创建时间或最近更新时间
- **R12** 新增卡片入口必须先选择模板，再创建实例，再跳转该实例的编辑页。
- **R13** 公开页、历史记录、联系方式申请 / 审批、分享路径都必须继续围绕具体 `shareCardId` 运作，不得在多实例模型下回退到 `sceneKey` 唯一定位。

### 3.5 后端边界

- **R14** 后端 `createCard(...)` 不得再通过 `findOwnedCard(userId, sceneKey)` 把“新增”降级为“确保存在”。
- **R15** 后端必须引入明确的“模板资格校验”和“卡片实例创建”两步，不得再混在同一逻辑里。
- **R16** `my-cards` 返回必须按实例维度返回，而不是按场景唯一项返回。
- **R17** 配置绑定、公开页读取、历史记录、联系方式申请、后台治理都必须继续以 `shareCardId` 作为实例事实源。

### 3.6 后台治理边界

- **R18** 后台分享卡治理页必须支持查看同一用户同一模板下的多张卡片实例。
- **R19** 后台必须能区分模板资格状态与已创建实例数量，不得把二者继续混为一体。
- **R20** 后台默认卡治理必须继续存在，并能在多实例模型下正确标注哪张卡为默认卡。

### 3.7 治理要求

- **R21** 本问题必须通过独立 Spec 固化，不得混入编辑页 UI 清理 Spec。
- **R22** 本 Spec 必须明确声明：旧会员 / 命理 / 受众视角 UI 清理由独立 Spec 处理，不在本轮覆盖。
