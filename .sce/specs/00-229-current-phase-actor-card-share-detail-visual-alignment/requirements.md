# 演员卡分享详情旧版结构与 3.0 视觉对齐

> 状态：参考结构纠偏完成（2026-08-20）。
>
> 用户裁决：生成预览与分享详情继续共用结构化渲染器；旧分享页的画布尺寸、模块坐标、悬浮导航、正文顺序和信息密度必须原样保留，只允许将界面色彩替换为 3.0 蓝白体系。

## 1. 概述

`00-228` 已解决生成页把主视觉冒充完整演员卡的问题，但第一版共享渲染器只提供资料卡和四个素材模块，明显少于旧 `pkg-card/ai-profile-card-detail` 的成熟分享结构。历史临时资源还会让每个 `t-image` 各自显示加载点，用户看到同一页同时出现多处“...”并误以为页面重复加载。

本 Spec 在不复制第二套正文的前提下，将旧分享页的沉浸主视觉、统计、完整资料、形象语言、技能、简介、经历、两列照片、视频和 PDF 页图结构迁移到 `ActorCardRenderer`，并统一使用 3.0 蓝白 Token。

2026-08-20 首轮实现虽然补齐了内容，却把旧分享页重新编排成“白色顶部导航 + 头像全铺 + 白卡叠层”，不符合用户参考图。纠偏以 `pkg-card/ai-profile-card-detail` 的经典布局和用户截图为唯一结构基线，不再接受仅包含相同模块但坐标、层级或顺序不同的近似实现。

## 2. 用户故事

- 作为卡主，我希望发布前预览就是完整分享详情，而不是若干简化卡片。
- 作为观看者，我希望分享页能连续阅读演员资料、作品、照片、视频和附件页图。
- 作为用户，我希望页面只有真正的数据请求加载态，单张媒体加载不再同时显示多组点状加载动画。
- 作为维护者，我希望生成预览与公开详情继续使用同一正文组件，避免再次分叉。

## 3. 功能需求

### 3.1 单一加载语义

**验收标准**：

- 页面数据请求期间只由 `generate/index` 或 `view/index` 外壳展示一次加载状态。
- `ActorCardRenderer` 内媒体使用微信原生 `image` 稳定性例外，不渲染 TDesign 默认点状 loading/error 图标，并保留稳定尺寸与明确失败块。
- `http://tmp/...`、`https://tmp/...`、`wxfile://...` 等不可持久访问资源不得传给图片组件。
- 单张图片失败不得锁住页面，也不得触发整页重新加载。

### 3.2 旧分享页完整信息架构

**验收标准**：

- 主视觉必须使用 `750 × 1334rpx` 固定画布比例，背景优先使用演员卡已选 `backgroundImageUrl`，不得用普通头像替代完整分享视觉。
- 经典布局七个区域必须沿用旧页设计坐标：`identity(81,203,233,291)`、`facts(83,579,285,184)`、`skills(420,579,255,184)`、`works(84,802,582,112)`、`photos(80,929,591,116)`、`intro(81,1077,281,159)`、`video(416,1077,263,159)`。
- 姓名、基础元信息、风格和合作信息必须位于 Hero 左侧透明区域；基础资料、技能、作品、照片条、简介和视频必须位于对应坐标，不得收进 Hero 底部统一白卡。
- 正文固定依次提供：统计摘要、基础信息、形象与语言、技能特长、个人简介、拍摄经历、照片展示、视频简历、PDF 简历。`settings.order` 不再改变分享详情的视觉顺序，但 `showVideo`、`showAttachment`、`showContact` 等显隐开关继续生效。
- 作品使用封面 + 文字摘要；照片使用旧分享页的两列稳定网格；视频提供可播放区域。
- PDF 附件页图直接嵌入长页并可点击预览；没有页图时保留“查看附件”降级入口。
- 空字段使用“待完善”或合理空态，不虚构演员信息。

### 3.3 3.0 蓝白视觉

**验收标准**：

- 用户选择的完整分享背景图作为内容资产保持原样；背景上的信息面板、标签、边框、正文画布和操作按钮使用蓝白 Token 替换旧棕色/米色界面色。
- 页面正文画布使用白色/浅灰分组；品牌蓝只用于主操作、选中态、链接和标签。
- 删除旧分享页的米黄背景、棕色边框、棕色标签和黑色主按钮。
- Hero 面板保持旧页的透明/半透明叠层形态和原坐标，不得因蓝白迁移改成新的卡片布局。
- 字体、间距、圆角和颜色只使用 `$kp-*` Token。

### 3.4 顶部导航与首屏起点

**验收标准**：

- `generate/index` 与 `view/index` 的正常内容态不显示白色 `KpPageNav`。
- 两页使用 `KpFloatingBackButton` 悬浮在 Hero 上，顶部不为导航单独保留白色高度，Hero 从页面滚动内容的 `y=0` 开始。
- 返回按钮继续基于微信胶囊位置自适配，不手写桌面坐标，不改变加载态和错误态的可读性。

### 3.5 公开页操作栏

**验收标准**：

- `pkg-actor-card/view/index` 底部固定显示“分享页面 / 联系演员”操作栏并预留安全区。
- 分享按钮通过 `onShareAppMessage` 分享当前 `cardId`、演员名称和有效主视觉。
- 有公开联系电话时允许拨打；无电话时按钮明确禁用并显示“未填电话”。
- `generate/index` 继续保留“回名片夹 / 生成或发布”操作栏，不在渲染器内部复制操作按钮。

### 3.6 兼容性展示模型

**验收标准**：

- `ActorCardPublicRespDTO` 只新增可选字段，不修改或删除 00-215/00-228 已有字段；新增 `backgroundImageUrl` 直接承载演员卡已有背景资源，不修改数据库。
- 快照字段优先；演员档案仅补齐快照缺失的性别、年龄、体重、院校、形象、语言、技能和认证状态。
- 已绑定 PDF 的签名页图随同演员卡响应返回，公开观看者无需调用需登录的 owner 素材接口。
- 数据库零变化；旧前端忽略新增字段后继续可用。

## 4. 非功能需求

- 共享渲染器保持分包自包含，不 import API、Pinia store 或主包业务模块。
- 图片、视频、PDF 容器使用稳定尺寸或宽高比，不因加载和失败改变版式。
- 生成页与公开页必须把长页 `scroll-view` 约束在视口内；内容可滚动到底，底部操作栏不得遮住最后一个附件页。
- `src`、`dist/build/mp-weixin`、`dist/dev/mp-weixin` 三侧结构、样式与 scope hash 一致。
- 运行态至少核验 `generate?preview=1` 与已发布 `view` 的首屏、正文、照片、附件及底部栏；首屏必须和用户参考图逐区截图对比。

## 5. 非目标

- 不恢复 1.0 `share_card` 数据链路、收藏或联系申请审批流程。
- 不生成单张超长位图、海报或新 PDF。
- 不修改演员卡表结构，不迁移历史临时资源。
- 不重新生成、重绘或改色用户已经选择的完整分享背景图片；“修改颜色”仅指界面层色彩 Token。
- 不改变素材库三列网格；两列规则仅属于演员卡分享正文。

## 6. 发布兼容

- 后端响应字段为新增型，旧小程序不受影响。
- 新前端依赖新增展示字段和附件页图时，后端需先发布或前后端同批发布。
- 数据库零迁移；附件页签名沿用现有 10 分钟访问 URL。
- 若档案或 PDF 页图读取失败，接口降级返回已有演员卡字段，不能让整张卡 500。
