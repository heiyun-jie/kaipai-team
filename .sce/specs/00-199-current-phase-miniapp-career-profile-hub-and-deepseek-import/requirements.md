# 00-199 当前阶段小程序职业资料夹与 DeepSeek 智能导入

> 状态：规划中 | 优先级：最高
>
> 依赖：`00-05`、`00-27`、`00-62`、`00-69`、`00-73`、`00-144`、`00-190`、`03-04`、`05-02`、`05-04`、`05-13`、`05-19`
>
> 记录目的：把用户于 `2026-07-22 ~ 2026-07-23` 确认的“小程序个人中心简化、个人档案去长表单、作品库与素材库独立、微信收藏文本经 DeepSeek 识别填充、DeepSeek 必须后台配置”提升为当前小程序正式主线，防止只改页面外观而继续保留旧数据事实源、旧上传入口和伪分析口径。

## 1. 背景

当前 `pages/mine/index` 同时承担账号首页、伪分享数据看板、创建分享、邀请二维码和设置库存，用户进入后需要扫描大量与当前任务无关的内容。代码中的“我分享了”实际使用卡片数量，“被打开”实际使用当前用户浏览过的历史数量，趋势图由前端合成，不具备真实近 30 天分析语义。

当前 `pages/actor-profile/edit` 又同时承载：

- 档案摘要与完整度运营
- 基础资料
- 形象与语言标签
- 照片分类上传
- 最多 10 条经历编辑
- PDF 简历
- 单个视频简历
- 全局 AI 润色面板、配额与历史

真实用户资料常长期保存于微信收藏纯文字笔记。用户提供的“演员王火火”测试样本包含基本资料、院校专业、职业能力、语言、角色类型、已播 / 待播 / 舞台 / 横屏等约 29 条作品，以及 `[图片] / [视频]` 占位。要求用户手动把这些内容重新拆进长表单，成本高且容易漏填。

本 Spec 的目标不是让 AI 自动改写或直接保存用户档案，而是建立以下正式闭环：

```text
微信收藏纯文字
  -> 用户主动读取剪贴板
  -> 后端 DeepSeek 结构化提取
  -> 候选值、原文证据、置信度与冲突复核
  -> 用户确认
  -> 个人档案 + 不限量作品库
  -> 素材库补照片、视频与 PDF
  -> 公开档案 / 分享卡按引用选择内容
```

## 2. 范围

### 2.1 本轮必须处理

- 个人中心重组为“职业资料夹”
- 个人档案收口为核心资料、职业资料、自我介绍和智能导入入口
- 作品库从档案长表单中独立，并取消前端 10 条上限
- 照片、视频和 PDF 统一进入素材库
- DeepSeek 资料结构化提取、候选复核、冲突合并和原子应用
- 后台 DeepSeek 配置、密钥治理、测试连接、启停和审计
- 头像、作品、素材、公开档案和分享卡之间的引用关系
- 历史头像、照片、视频、PDF、经历与分享配置迁移
- 公开页、作品集、创建分享、分享卡和 AI 分享图消费者切换
- `pkg-profile` 分包与包体治理
- 王火火测试账户固定样本验收
- 旧 Spec 条款、旧静态验收脚本和旧字段的分阶段接管 / 退场

### 2.2 本轮不处理

- 从微信收藏直接读取图片、视频或文件
- 图片 OCR、PDF 文本解析、语音转文字
- DeepSeek 自动上传或生成媒体素材
- 恢复个人中心伪数据卡
- 在小程序前端直连 DeepSeek
- 用现有规则型 AI 润色适配器冒充结构化导入
- 让模型修改实名认证性别、实名姓名或身份证信息
- 一次性删除所有旧字段；物理删除必须在消费者切换后独立审计
- 新增个人中心分享分析页；真实分享分析继续由后端 / 后台统计域承接

## 3. 术语与优先级

- **核心资料**：头像、公开名称、性别、年龄、身高、当前城市。
- **职业资料**：体重、籍贯、院校、专业、语言 / 方言、职业特长、人物类型 / 戏路、职业能力。
- **作品库**：以现有作品记录 ID 为基础、数量不限的演员作品事实源。
- **素材库**：统一管理照片、视频、PDF 及处理状态的私有资产库。
- **候选值**：DeepSeek 返回并经后端校验、但尚未由用户确认写入的值。
- **原文证据**：支持某个候选值的原始输入片段，只允许存在于当次响应与前端内存草稿。
- **代表作**：用户从作品库选择、默认用于公开档案的最多 6 条作品。
- **当前简历**：用户从多个 PDF 素材中明确设置的一份当前 PDF。

优先级规则：

- 本 Spec 自生效起，只对明确列出的冲突条款进行接管；旧 Spec 继续保留历史追溯价值。
- `00-73 R15` 中关于 mine 的数据卡、趋势、双动作卡、二维码和旧设置结构，由本 Spec 替代；其他 6 个 reference screen 合同继续有效。
- `00-144` 对 mine 的评分基线改为本 Spec；95 分、四层证据和低分继续修改门禁继续有效。
- `00-190` 保留“游客进入我的不强登、账号动作点击后登录”，旧游客数据区 / 二维码 / 旧设置项合同由本 Spec 替代。
- `03-04 / 05-02 / 05-13 / 05-19` 中位于个人档案页内的作品、照片、视频、PDF 和完整度运营结构，由本 Spec 替代。
- `05-04` 的 AI 润色合同不等同于本 Spec 的资料导入；二者必须使用不同入口、接口、配置、配额和字段白名单。

## 4. 功能需求

### 4.1 个人中心职业资料夹

- **R1** `pages/mine/index` 必须删除“我的数据”卡、近 30 天、趋势图、卡片 / 海报 / 再进入子统计及相关错误态。
- **R2** 个人中心不得再把卡片数量展示为分享次数，也不得把浏览历史数量展示为被打开次数。
- **R3** 个人中心必须删除“我的二维码”入口；当前邀请二维码能力不得继续伪装为个人名片二维码。
- **R4** 账号头部只展示头像、公开名称和 `当前城市 · 演员账号 · 用户 ID`，不再保留与“个人档案”重复的编辑按钮；当前城市缺失时直接省略该段，不显示 `--`。
- **R5** “我的资料”必须包含三个平级入口：`个人档案 / 作品库 / 素材库`。
- **R6** 个人档案摘要显示核心资料状态和职业资料数量；作品库摘要显示作品总数和代表作数；素材库摘要显示照片数、视频数和当前 PDF 状态。
- **R7** “常用功能”只保留 `创建分享 / 联系申请 / 设置`。
- **R8** 创建分享必须降为普通入口，不再作为首屏双主动作卡。
- **R9** 联系申请仅在有待处理项时显示真实数量。
- **R10** 收藏的分享并入 `pages/history/index` 的“记录”体系，以 `浏览记录 / 收藏` 分段视图承接；不在个人中心重复提供入口，旧收藏页只允许短期兼容跳转。
- **R11** 消息通知、偏好设置、用户协议、隐私政策、关于和退出登录统一由独立“设置”页承接，不得继续把这些条目直接平铺在个人中心。
- **R12** 页面不得恢复装饰性英文副标题、伪分析图或完成度运营卡。
- **R13** 删除个人中心伪数据卡不等于删除后端真实分享统计域；真实统计继续由正式 analytics 事实源治理。

### 4.2 游客态

- **R14** 未登录用户点击底部“我的”后必须停留在 `pages/mine/index`，不得在页面展示阶段直接跳登录。
- **R15** 游客账号头部显示未登录状态和登录入口。
- **R16** 游客可看到个人档案、作品库和素材库三个入口名称，但不得显示 `0`、`--` 或任何伪造数量。
- **R17** 游客点击个人档案、作品库、素材库、创建分享或联系申请时才进入登录流程。
- **R18** 游客可直接查看设置中的协议、隐私政策和关于页面。
- **R19** 游客态不得发起档案、作品、素材、联系申请或 DeepSeek 能力等需要 token 的请求。
- **R20** 已登录账号头部继续使用全局 user store；附属状态同步失败不得把账号降级为游客。

### 4.3 个人档案简化

- **R21** `pages/actor-profile/edit` 只负责头像引用、核心资料、职业资料、自我介绍和智能导入入口。
- **R22** 核心资料保存门槛继续要求：头像、公开名称、性别、年龄、身高、当前城市。
- **R23** 头像不得在档案页维护第二套上传流程；档案页只显示当前头像并进入素材库选择照片。
- **R24** 素材库为空时，更换头像流程必须先引导上传照片，再返回选择结果。
- **R25** 职业资料必须支持：体重、籍贯、院校、专业、语言 / 方言、职业特长、人物类型 / 戏路、职业能力。
- **R26** 职业资料默认折叠，只显示真实摘要，不把自动识别出的字段继续铺成首屏长表单。
- **R27** 手动编辑必须始终可用；DeepSeek 不可用或识别失败不得阻断档案保存。
- **R28** 档案页必须移除照片分类、作品经历、视频、PDF、完整度百分比、提升建议和全局 AI 润色大卡。
- **R29** AI 润色改为字段就近入口：自我介绍在档案页，作品描述在单条作品编辑页。
- **R30** 档案页底部只保留一个“保存资料”主操作。
- **R31** 有未保存变更时离开档案页，必须提示保存、放弃或继续编辑。

档案页中的头像选择、核心资料、职业资料和自我介绍必须先保留为同一页面草稿，并由“保存资料”一次提交；不得用多个独立请求制造部分成功状态。

### 4.4 不限量作品库

- **R32** 作品库必须以现有 `actor_experience` 记录为唯一作品事实源，不得复制出第二套长期并行作品主表。
- **R33** 必须移除前端最多 10 条作品门禁，作品库数量不得设置产品级固定上限。
- **R34** 每条作品至少支持：项目名、播出状态、作品类型、角色层级、角色名、拍摄 / 播出时间、同期声状态、合作演员、项目成绩、描述、来源状态。
- **R35** 项目名为必填；原文未提供时间、类型或状态时保持未知，不得由模型补造。
- **R36** 作品必须支持已播、待播、舞台、横屏及其他分类筛选，同时允许更细的作品类型编码。
- **R37** 用户可设置最多 6 条默认代表作，并可调整顺序。
- **R38** 公开档案默认展示代表作；创建分享默认继承代表作，但允许每张分享卡重新选择。
- **R39** 分享卡只保存作品引用和顺序，不复制作品正文。
- **R40** 重复作品必须按标准化项目名、标准化角色名和用户范围生成去重键，并具备数据库级 active 唯一约束；不得仅按数组位置或事务内先查后写判断。
- **R41** 删除被代表作、公开档案或分享卡引用的作品前，必须展示影响并要求用户确认替换或解除引用。
- **R42** 作品库必须支持搜索、分类筛选、手动新增、编辑、设为代表作、关联素材和删除。
- **R43** 作品库必须提供“从剪贴板导入作品”入口，并复用同一 DeepSeek 结构化提取合同；`works_only` 场景不得因头像、性别或当前城市未完善而阻断作品写入，必要时只创建不可公开的未完成档案壳。

### 4.5 素材库

- **R44** 照片、视频和 PDF 必须统一由素材库管理，其他页面只从素材库选择。
- **R45** 照片分类至少支持：头像候选、模卡、形象照、生活照、剧照、造型照、其他。
- **R46** 视频分类至少支持：自我介绍、作品片段、表演片段、其他。
- **R47** 图片继续支持不限数量；视频支持多条，不得继续只依赖单个 `videoUrl`。
- **R48** PDF 支持多个历史文件，但同一演员只能有一份当前简历；当前简历必须由 `actor_profile.current_resume_asset_id` 单值引用表达，切换时在同一事务内完成，不用通用关系表模拟唯一性。
- **R49** PDF 继续保留格式 / 大小校验、PDFBox 转图片页、有序页和失败闭锁能力。
- **R50** 头像必须引用照片素材；作品剧照 / 视频必须通过作品素材关系引用；分享卡必须通过分享素材关系引用。
- **R51** 新上传素材默认仅自己可见，底层对象必须位于私有 Bucket / 私有 ACL，不得把永久可访问 URL 当成权限边界；未建立公开关系时不得被公开接口返回。
- **R52** 只有用户明确把素材加入公开档案或分享卡后，素材才允许通过鉴权下载代理或短时签名 URL 对外展示；所有者预览与公开展示必须分别校验权限和引用场景。
- **R53** 历史素材迁移时必须保持当前已公开行为，不能因为“新素材默认私有”让历史公开内容消失。
- **R54** 删除被头像、作品、公开档案或分享卡引用的素材前，必须展示引用范围并阻止无提示删除。
- **R55** 上传失败或 PDF 转换失败的素材不得进入可选择状态，必须保留明确失败原因和重试入口。
- **R56** 素材库必须支持预览、重命名、分类、关联作品、设为头像、设置当前 PDF 和删除。
- **R57** 素材文件本身不得发送给本轮 DeepSeek 文本识别能力。
- **R58** 剪贴板中的 `[图片] / [视频]` 只生成补素材提示，不得创建空素材记录。
- **R59** 个人档案、作品编辑和创建分享中不得保留互相独立、长期并行的上传事实源。

### 4.6 DeepSeek 智能导入

- **R60** 首版输入只支持微信收藏中的纯文字 / 笔记经用户复制后导入。
- **R61** 小程序不得在进入页面时自动读取剪贴板；只有用户主动点击后才调用剪贴板 API。
- **R62** 读取后必须展示可编辑原文预览，用户再次确认后才向后端发送。
- **R63** 前端不得直连 DeepSeek；所有模型调用必须由后端封装。
- **R64** 资料导入必须使用独立 `/api/ai/profile-import/*` 能力，不得复用 `/api/ai/polish-resume`。
- **R65** 导入只要求登录，不要求先实名认证，避免首次建档与实名认证完成度形成循环。
- **R66** 原始文本只用于当次识别，不写业务数据库、不写 Redis 草稿、不写普通日志、不进入失败样本正文。
- **R67** 后端只允许记录请求 ID、用户 ID、配置 ID、模型、输入长度、候选 / 作品 / 冲突数量、耗时、状态和脱敏错误码。
- **R68** DeepSeek 必须返回约束后的结构化 JSON；纯自然语言结果不得进入候选复核。
- **R69** 模型 JSON 不可解析时允许一次受控修复重试；仍失败则返回明确错误且不写业务数据。
- **R70** 每个档案候选至少包含 `candidateId / fieldKey / candidateValue / confidence / sourceText / sourceType / warning / selected / requiresExplicitConfirmation / confirmed`。
- **R71** 每个作品候选必须包含 `candidateId / matchStatus / matchedExperienceId / selectedAction`，以及项目、角色、状态、类型、成绩等逐字段结构化值、证据和冲突；`selectedAction` 只允许 `create / merge / skip`。
- **R72** 识别结果必须按个人资料、作品、需确认项、疑似重复和未映射内容分组，不得形成几十项连续长表单。
- **R73** 识别失败、超时或网络中断时，前端原文必须保持可编辑并允许重试或回到手动编辑。

### 4.7 候选、冲突与性别推断

- **R74** 空白字段且证据明确的候选默认选中。
- **R75** 已有字段与候选相同的项标记为无需修改。
- **R76** 已有字段与候选冲突时默认不覆盖，必须并排展示原值、候选值和证据。
- **R77** 低置信度或任何推导字段默认不选中；角色证据性别推断即使满足规则，也必须由用户执行独立确认动作后才允许选中。
- **R78** `籍贯`不得映射为当前城市；当前城市缺失时继续要求用户补充。
- **R79** `2004.9` 等部分生日必须保存出生精度，不得伪造成某月 1 日；年龄候选可以按当前日期动态推算并标明来源。
- **R80** 榜单、热度、播放量和合作演员必须保留原文事实，不得由模型润色数字或补造。
- **R81** 当原文连续、一致地包含多条“女主 / 女二 / 女反一”等角色证据时，允许生成 `gender=female` 候选。
- **R82** 角色证据推断的性别必须标记 `sourceType=inferred_from_roles` 与 `requiresExplicitConfirmation=true`，默认 `selected=false / confirmed=false`；用户执行独立确认后，apply 才允许写入公开档案。
- **R83** 角色证据冲突或只有单条弱证据时，不得默认选中性别候选。
- **R84** 不得仅凭姓名、头像风格、院校或专业推断性别。
- **R85** 推断性别只写演员公开档案字段，不得修改实名认证信息。
- **R86** 已有作品重复导入必须幂等跳过或进入明确合并确认，不得重复创建。
- **R87** 用户确认前，DeepSeek 提取接口不得直接写个人档案、作品或素材。

### 4.8 后台 DeepSeek 配置

- **R88** DeepSeek 未在后台配置并启用前，小程序智能导入不得调用模型。

- **R99** 资料导入必须拥有独立权限、配置表、审计表和调用审计，不得写入生图 provider 配置表。

- **R107** 不得使用缺少数据库目标校验的通用 `owner_type / owner_id` 多态关系替代所有引用表。
- **R108** 分享卡和公开页读取作品 / 素材时必须使用正式关系与统一 resolver，不得继续拼接旧 JSON 数组。
