# 00-74 当前阶段后台参考稿 UI 与架构重构（Current Phase Admin Reference UI Architecture Rebuild）

> 状态：进行中 | 优先级：最高 | 依赖：00-11 platform-admin-console，00-71 admin-console-reference-ui-implementation，00-72 current-phase-admin-information-architecture-alignment
> 记录目的：把用户基于 `D:\XM\kaipai-team\_-_1.html` 与当前线程补充的逐页后台截图所提出的“按对比后的 UI 页面和当前架构继续推进后台重构”提升为独立 Spec，区别于 `00-71` 的首轮后台壳层落地与 `00-72` 的两入口收口阶段，明确当前新目标是：在不伪造后端能力的前提下，把登录后的正式后台信息架构重新拉回 reference 的 8 页屏流。

## 1. 背景

当前后台已经存在三层彼此冲突的事实：

1. `00-71` 已把 `kaipai-admin` 的登录页、公共壳层和工作台视觉收口到 `D:\XM\kaipai-team\_-_1.html` 的米白控制台语言。
2. `00-72` 随后把登录后主导航进一步收口成：
   - 控制台 / 渠道分析
   - 用户中心（分享卡治理 / 联系方式申请）
3. `2026-04-21` 当前线程里，用户又补充并确认了一组后台逐页 reference 截图，覆盖：
   - 仪表盘
   - 数据分析
   - 用户管理
   - 分享内容
   - 风格模板
   - 运营动作
   - 系统设置

在对当前运行态与 reference 做真实对比后，已经确认：

- 当前后台只剩 3 个正式入口：
  - `/dashboard/index`
  - `/content/share-cards`
  - `/content/contact-requests`
- 左侧导航、页面 eyebrow、工作台说明与 `admin-information-architecture.ts` 都仍然沿用 `00-72` 的“主导航已收口”口径。
- 参考稿表达的则是一套更完整的后台正式信息架构：
  - `OVERVIEW`：仪表盘、数据分析
  - `GROWTH`：用户管理、机构管理、分享内容
  - `OPERATE`：风格模板、运营动作、系统设置

这说明当前偏差已经不是“样式还没抠齐”，而是：

- 当前后台正式信息架构与 reference 页面职责发生了系统性漂移。

另外，本轮还发现了两类关键 runtime 证据：

### 1.1 已存在但未进入正式架构的能力

- 后端真实存在业务用户中心接口：
  - `GET /admin/users`
  - `GET /admin/users/{id}`
- 前端真实存在对应 API / 类型：
  - `src/api/user-center.ts`
  - `src/types/user-center.ts`
- 前端还存在占位视图：
  - `src/views/user/UserCenterView.vue`

这证明“用户管理”不是纯概念缺口，而是已有 runtime source、前端页面未真正接入正式导航。

### 1.2 仍然缺失明确事实源的页面

经核查，`机构管理` 当前没有与 reference 一一对应的正式后台路由、页面实现或独立后端接口；当前仅能在招募治理链路里看到 `companyName / companyProfileId` 等片段信息，尚不足以支撑一张 reference 级正式机构管理页。

因此，本轮不应继续把工作记在 `00-72` 的“两入口主架构收口”里；更合理的做法是新增一个后续 Spec，专门承接：

- 后台 reference UI / IA 的二次重构
- reference 页面职责与当前 runtime capability 的重新映射
- `00-71 -> 00-72 -> 00-74` 的阶段 handoff

## 2. 范围

### 2.1 本轮必须处理

- 固化 `D:\XM\kaipai-team\_-_1.html` 与用户补充的逐页后台截图为当前后台 reference-driven 重构的唯一 UI / IA 基线
- 明确 reference 正式后台架构的 8 个页面状态：
  - 仪表盘
  - 数据分析
  - 用户管理
  - 机构管理
  - 分享内容
  - 风格模板
  - 运营动作
  - 系统设置
- 明确这 8 个页面与当前真实后台能力之间的映射关系：
  - 直接复用现有页面
  - 复活已有 API / 占位页
  - 允许新建前端容器页以重组已有能力
  - 明确标记当前仍无事实源的缺口页
- 重新定义正式后台导航与隐藏治理工具的边界
- 回填 Spec 索引、Spec↔代码映射与 steering 当前上下文

### 2.2 本轮不处理

- 重新设计登录页；登录页继续沿用 `00-71` 已完成结果，只做一致性回归验证
- 新增后台业务域能力、后端统计模型、权限系统或数据库表
- 因为 reference 看起来完整，就伪造 `机构管理 / 运营动作 / 系统设置` 的假数据
- 删除旧治理工具链路本身；它们可以从正式导航退回，但不在事实未核实时直接物理移除
- 把前台 `00-73` reference 重构混入本 Spec

## 3. 需求

### 3.1 参考基线与证据优先级

- **R1** `D:\XM\kaipai-team\_-_1.html` 必须被视为当前后台 reference-driven 二次重构的唯一总览基线。
- **R2** 用户在 `2026-04-21` 当前线程补充的逐页后台截图，若与 `_-_1.html` 的总览解读存在冲突，则对对应页面的 block order、CTA、筛选结构与信息密度拥有更高优先级。
- **R3** 本 Spec 只适用于 `D:\XM\kaipai-team\kaipai-admin` 的登录后正式后台，不覆盖前台小程序和 `D:\XM\kaipai-team\_-_.html`。
- **R4** 本轮所有判断必须优先服从真实运行态与真实接口，而不是仅根据截图猜测页面能力是否存在。

### 3.2 当前阶段后台正式信息架构

- **R5** 登录后后台正式导航必须恢复到 reference 的三组结构：
  - `OVERVIEW`
  - `GROWTH`
  - `OPERATE`
- **R6** 上述三组下的正式页面状态必须收口为 8 个 reference 页面：
  - 仪表盘
  - 数据分析
  - 用户管理
  - 机构管理
  - 分享内容
  - 风格模板
  - 运营动作
  - 系统设置
- **R7** `00-72` 的“两入口主导航”必须被视为历史收口阶段，而不是当前继续推进的最终目标。
- **R8** 当前仍保留的治理工具页不得继续伪装为正式 reference 页面；它们只能属于：
  - 隐藏治理工具
  - drill-down 子页
  - reference 外辅助页

### 3.3 页面职责与能力承接边界

- **R9** `仪表盘` 当前必须继续由 `/dashboard/index` 承接，但页面合同需重新回到 reference 的大盘结构，而不是继续停留在“主导航已收口”的阶段说明页。
- **R10** `数据分析` 当前可以新增为独立后台路由或 `dashboard` 下的独立正式页面状态，但其数据来源必须继续只使用现有 `/admin/dashboard/overview` 与现有真实聚合字段，不得新增伪分析接口。
- **R11** `用户管理` 当前必须优先复用真实存在的 `/admin/users` 与 `/admin/users/{id}` 能力；`system/admin-users` 只代表后台账号治理，不得再被当作业务用户管理页替身。
- **R12** `分享内容` 当前必须优先复用 `content/share-cards` 的真实页面能力，但页面语义需要从“治理表格”回收为 reference 的正式内容浏览 / 运营页表达；旧治理字段可下沉到详情、抽屉或辅助模式中，不得继续主导页面第一语义。
- **R13** `风格模板` 当前必须优先复用 `content/templates` 的真实页面能力，但页面语义需要从“配置台账”回收为 reference 的模板库 / 卡片网格表达；发布、回滚、启停用等高风险动作可以保留为卡片内操作或二级抽屉。
- **R14** `运营动作` 与 `系统设置` 当前允许新建前端正式容器页，但只能重组已有页面、已有统计字段和已有治理动作，不得借机新增后台业务能力。
- **R15** `机构管理` 当前必须先完成事实源审计；在没有足够 runtime source 前，只允许作为带“事实源待补齐”说明的正式壳页存在，不能伪造列表、统计或详情数据。

### 3.4 导航、路由与权限合同

- **R16** 当前正式侧栏不得继续直接沿用 `00-72` 的两入口 `adminSidebarMenus` 投影；必须重新定义与 reference 对齐的正式导航投影。
- **R17** `adminMenus` 与 `router/index.ts` 仍需保留全量能力库存，但必须明确区分：
  - 正式 reference 页面
  - 隐藏治理工具
  - 候删或仅兼容页面
- **R18** 新增的正式容器页在第一阶段不得强依赖新增后端权限码；若当前 capability carrier 已存在页面权限，应优先复用现有权限边界。
- **R19** 顶部栏、breadcrumb、搜索框、日期切换、通知入口与导出按钮的显隐关系，必须重新回到 reference 页面语义，而不是继续沿用 `CURRENT PHASE / 主导航已收口` 的阶段性语言。

### 3.5 视觉与页面合同

- **R20** 仪表盘必须对齐 reference 的 page contract：
  - 顶部轻量控制条
  - 4 张 KPI 大卡
  - 转化漏斗
  - 趋势区
  - 留存 / 风格偏好 / 渠道分布
- **R21** 数据分析必须对齐 reference 的 page contract：
  - 页内 tabs
  - 渠道表现表
  - 流量构成 donut
  - 洞察说明块
- **R22** 用户管理必须对齐 reference 的 page contract：
  - 顶部统计卡
  - 用户类型 tabs
  - 搜索 / 高级筛选 / 新增用户入口
  - 用户列表主表
- **R23** 分享内容、风格模板、运营动作、系统设置必须分别对齐 reference 的卡片墙、模板库、动作列表和分组设置页合同；但其内部按钮和数据来源仍须保持真实 runtime 边界。
- **R24** `机构管理` 因当前缺少单页截图与明确 runtime source，第一阶段只要求保留 reference 中的正式导航位置与页级壳层，不允许冒充已完成 reference 级页面。
