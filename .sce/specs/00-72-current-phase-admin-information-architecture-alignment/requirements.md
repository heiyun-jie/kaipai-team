# 00-72 当前阶段后台信息架构对齐（Current Phase Admin Information Architecture Alignment）

> 状态：已完成 | 优先级：最高 | 依赖：00-11 platform-admin-console，00-69 current-phase-share-analytics-architecture-refactor，00-71 admin-console-reference-ui-implementation
> 记录目的：在 `00-71` 已完成后台控制台视觉基线、公共壳层和登录页改造的前提下，把 `D:\XM\kaipai-team\_-_1.html` 的控制台语言与当前架构真正收口到“控制台 / 渠道分析 + 用户中心”，明确主导航、兼容保留页和旧业务域退出边界，避免继续在新的视觉外壳下保留旧后台信息架构。

## 1. 背景

当前后台存在两层已经分叉的事实：

1. `00-71` 已把 `kaipai-admin` 的视觉壳层、工作台和登录页收口到 `D:\XM\kaipai-team\_-_1.html` 的控制台语言。
2. `00-69` 已明确当前阶段后台主架构应收口为：
   - 控制台 / 渠道分析
   - 用户中心

但实际代码里仍同时保留：

- `src/constants/menus.ts` 中完整的旧多业务域菜单清单：
  - `verify`
  - `referral`
  - `recruit`
  - `membership`
  - `payment`
  - `refund`
  - `content`
  - `system`
- `src/router/index.ts` 中对应的大量活跃路由
- 只有 `adminSidebarMenus` 已局部收口为两类导航：
  - `控制台 / 渠道分析`
  - `用户中心`

这会导致三个问题：

- 视觉已经切到新控制台，但后台真实信息架构仍是旧多业务域并列
- 当前架构文档、左侧主导航、实际路由库存之间不再一致
- 后续若继续推进后台重构，会在“主架构页面”和“兼容保留治理页”之间持续混淆

因此，本轮不应重复新建一个“继续参考 `_-_1.html` 改样式”的 Spec；更合理的做法是新增一条后续 Spec，专门承接**后台信息架构对齐**。

## 2. 范围

### 2.1 本轮必须处理

- 固化当前阶段后台主架构只包含：
  - 控制台 / 渠道分析
  - 用户中心
- 明确 `00-71` 负责视觉基线，`00-72` 负责信息架构收口
- 明确当前所有后台页面的分类：
  - 主架构保留项
  - 兼容保留治理项
  - 删除候选项
- 为后续菜单、路由、标题、面包屑和页面入口清理提供单一 Spec 边界

### 2.2 本轮不处理

- 再次重做登录页视觉
- 再次整体改写 `00-71` 已经完成的壳层风格
- 直接删除所有旧后台页面
- 新增后台业务能力、接口、权限码或统计口径
- 把 `_-_1.html` 中 `analytics / users / orgs / shares / templates / actions / settings` 直接照搬为新路由规划

## 3. 需求

### 3.1 当前阶段后台主架构

- **R1** 登录页已由 `00-71` 承接完成；`00-72` 默认只处理登录后的后台主界面，不重新定义登录页产品边界。
- **R2** 登录后后台主导航当前阶段只允许保留两类顶层语义：
  - 控制台 / 渠道分析
  - 用户中心
- **R3** `控制台 / 渠道分析` 当前阶段必须由现有 `/dashboard/index` 承接，不新增独立 `analytics` 路由。
- **R4** `用户中心` 当前阶段只能由当前**已存在**的用户/分享相关页面承接，至少包括：
  - `content/share-cards`
  - `content/contact-requests`
- **R5** 若当前仓库内不存在可直接承接“用户个人信息列表 / 详情”的真实页面，则本轮不得因为架构图存在该概念而临时发明新页面或假入口。
- **R6** `D:\XM\kaipai-team\_-_1.html` 中出现的 `analytics / users / orgs / shares / templates / actions / settings` 只作为控制台布局语言参考，不得被当成当前后台真实路由规划。

### 3.2 旧业务域处理边界

- **R7** 以下旧业务域不得继续作为当前阶段后台**主导航**的一部分：
  - `verify`
  - `referral`
  - `recruit`
  - `membership`
  - `payment`
  - `refund`
  - `content/templates`
  - `content/default-general-card`
  - `system/*`
- **R8** 上述页面若当前仍承担运维、迁移、审计或兼容职责，只能被定义为“兼容保留治理页”或“隐藏工具页”，不能继续伪装成当前产品主架构页面。
- **R9** `system/admin-users`、`system/roles`、`system/operation-logs`、`system/ai-resume-governance` 必须被显式定义为后台治理工具，而不是当前阶段 `用户中心` 的组成部分。
- **R10** 本轮不允许为了填补参考稿中的布局块，新增任何新的后台菜单、页面、接口、统计字段或权限码。

### 3.3 菜单、路由与页面语义合同

- **R11** 当前阶段**可见主导航**必须以 `adminSidebarMenus` 或其后续等价投影为单一事实源，不能再以 `adminMenus` 原始全量库存直接驱动主导航。
- **R12** `adminMenus`、`router` 与页面清单必须被显式划分为：
  - 主架构可见页
  - 隐藏治理页
  - 删除候选页
- **R13** 工作台、面包屑、标题和快捷入口只允许指向当前阶段主架构页面，不能继续把旧业务域作为“默认正式入口”展示给用户。
- **R14** 当前后台文案中所有“旧多业务域并列”的产品表达，必须纳入清理计划，不得继续与当前架构并存。
- **R15** 登录页只做一致性回归验证，不再把它作为本轮主要设计变量。

### 3.4 分阶段治理与删除边界

- **R16** 本轮必须产出一份明确的后台页面分类矩阵，至少覆盖当前 `src/router/index.ts` 中全部登录后路由。
- **R17** 对任何旧页面的删除动作，必须先完成依赖审计，明确：
  - 是否仍被主导航引用
  - 是否仍被快捷入口引用
  - 是否仍承担兼容/运维职责
- **R18** 在依赖未核实前，不允许直接大面积删除后台页面；但也不允许继续把它们定义为当前产品正式信息架构。
- **R19** 本轮必须明确 `00-71 -> 00-72` 的 handoff：`00-71` 负责视觉基线，`00-72` 负责后台主架构收口。

### 3.5 治理要求

- **R20** 本轮必须通过独立 `00-72` Spec 固化后台信息架构收口边界，不能只口头说“按当前架构继续改后台”。
- **R21** 本轮必须把 `00-72` 回填到 `.sce/specs/README.md` 与 `spec-code-mapping.md`。
- **R22** 本轮必须给出后续最小实施顺序，供实际改造按阶段推进。
